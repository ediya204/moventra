# 账户与卡片风控统计模型

## 目标与边界

本模型用于只读运营调查，重点识别连续欠费、高拒绝率和大额欠费。它不替代正式授信、清结算或风控决策系统。

- 确认欠费金额只能来自服务端负余额、真实授信缺口或未来明确的 overdue 字段。
- 失败交易金额称为“拒绝影响金额”，不能作为欠费金额。
- 缺少历史欠费快照时，只能标记“疑似连续欠费”。
- 所有输出必须携带统计周期、返回条数、服务端总数、覆盖率和策略版本。

## 标准输入

分析引擎只依赖标准化事件，不绑定特定接口：

```ts
type TransactionEvent = {
  transactionId: string;
  accountId: string;
  cardId: string;
  occurredAt: number;
  status: 'success' | 'failed' | 'pending';
  amount: number;
  currency: string;
  merchantId?: string;
  merchantName?: string;
  failureCode?: string;
};
```

未来数据进入后，只需在 API 适配层映射成这些字段，统计算法不需要重写。

## 数据进入与重算约束

- 以 `transactionId` 做幂等去重，重复事件不进入分子或分母；
- 所有窗口使用事件发生时间 `occurredAt`，不用抓取时间；
- 迟到事件进入后按其事件时间重算受影响的 1/7/30/90 日窗口；
- 同一分析批次固定 `asOf`，保证主账户、子账户和卡片结果可复现；
- 非 USD 事件必须先按交易发生时汇率归一到统一报告币种，原币金额和汇率仍需保留；
- 每次结果保留策略版本、数据截止时间、去重数、返回数和服务端总数。

## 时间窗口

同时计算 1日、7日、30日和90日：

- 1日用于发现突发；
- 7日用于当前运营判断；
- 30日作为短期基线；
- 90日观察长期结构。

拒绝率：

```text
拒绝率 = 失败交易尝试数 / 全部交易尝试数
```

待处理交易保留在分母，退款是否进入尝试数应由后端事件类型进一步明确。

## 高拒绝率

不能只用原始比例。当前策略同时要求：

1. 样本量至少 8 笔；
2. 原始拒绝率至少 20%；
3. 95% Wilson 置信区间下界至少 10%。

Wilson 下界可避免 1 笔交易失败就被误判为 100% 高拒绝率。

## 连续与突发拒绝

- 每张卡按发生时间排序，计算最大连续失败序列；
- 连续 3 笔达到关注阈值；
- 使用滑动窗口计算任意24小时内最大失败笔数；
- 账户级取各卡最大连续序列，避免不同卡片事件交错后稀释信号。

## 连续欠费

确认连续欠费需要至少两个历史欠费快照，或服务端直接返回连续欠费天数。

当前只有单点资金风险快照时：

```text
当前确认欠费金额 > 0 且同卡连续拒绝 >= 2
=> 疑似连续欠费
```

该规则只能用于运营调查入口，不能作为正式欠费结论。

如果接口提供拒绝原因，疑似连续欠费只使用 `insufficient_funds`、余额不足或额度不足一类的连续拒绝；拒绝原因完全缺失时才回退到“任意连续拒绝”，并明确降低证据等级。部分覆盖不能静默回退。

## 大额欠费

当前 Demo 阈值为 USD 1,000，实际生产阈值应按币种、账户类型和历史分布配置。

```text
确认欠费金额 = max(abs(负的实际剩余), 真实授信缺口)
```

使用 `max` 而不是相加，避免两个字段描述同一风险敞口时重复计算。

## 金额和集中度

- 失败金额 P50/P95：观察典型和尾部拒绝影响；
- 商户 HHI：各商户交易金额占比平方和；
- HHI 高于 0.35 时提示商户高度集中；
- 失败金额仍不是确认欠费。

## 数据质量

```text
覆盖率 = 当前返回交易条数 / 服务端报告总数
```

同时记录拒绝原因覆盖率：

```text
拒绝原因覆盖率 = 有明确 failureCode 的失败交易 / 全部失败交易
```

- 高：覆盖率 >= 90% 且样本 >= 30；
- 中：覆盖率 >= 50% 且样本 >= 10；
- 低：其他情况。

置信度低时只能展示观察值，不应输出确定性的高拒绝率结论。

## 策略版本

全部阈值集中在 `src/config/riskPolicy.ts`，每次修改都必须更新策略版本。页面和未来导出结果应保留该版本，确保历史结果可复现。
