# V1 资金账本与对账规划

日期：2026-09-07。状态：DESIGN，依据本轮代码核查形成的实施方案；本文件不表示对账系统已实现，也不授权真实资金动作、迁移或部署。

配套文档：[领域规则](transactions-and-funds.md)、[接口契约](../api/contract.md)、[R01–R18 验收矩阵](../testing/financial-scenarios.md)。这些文件已同步本方案的口径；接口和验收要求仍为DESIGN。

## 一、目标与产品边界

对账首先回答四件事：客户还有多少钱；钱实际存放在哪里；每次增减由什么业务造成；内部记录与外部事实之间还有哪些差异。

**客户归属、卡资金分户、业务账本和审批归我们系统；Slash 只是上游。** 内部卡分户不要求 Slash 有逐卡独立余额。渠道账户、虚拟账户、卡额度均不能直接代替客户资产归属。

V1 验收标准：任意一个余额可以展开为期初、逐笔变动和期末；任意一笔变动可以追到订单、分录、审批及适用的上游证据；任意差异都有归属、责任人、时间及处理结果。余额相同不等于逐笔无漏记，内部借贷平衡也不等于上游没有漏单。

沿用用户确定的 Slash 手动同步，不增加独立“跨币种账户快照”菜单。对账所需的来源余额时点、采集批次与完整性在后台保留，并在对账详情中展示。缺少这些证据时不能宣布渠道资金已对平。

## 三、账目怎么分

### 3.1 内部客户分户

同一客户、同一币种下，主钱包与各卡分户是互不重叠的余额分配：

`客户账面余额 = 主钱包账面余额 + 各卡分户账面余额 + 已确认纳入此口径的其他独立子账户`

- 客户汇总行是上述分户的汇总，不再作为一个账户加一次。
- 已入账余额与占用分开；可用金额按该资金产品明确的有效占用、限制及未结义务规则派生。缺少授权占用来源时标明不完整，不把它作为真实出金依据。
- 内部管理转入：主钱包减少、卡分户增加，客户合计不变。
- 内部管理转出：反向分配，客户合计不变。
- 已确认消费、实际退款、客户应承担的独立费用分别形成变动。强制扣款必须有对手科目及业务凭证。
- 风控冻结是权限限制；资金预占是可用余额限制。两者均不天然形成收入或支出。

### 3.2 平台控制账户与外部资金

至少区分客户资金义务、平台自有资金、上游/链上实际资产、渠道结算应收应付、在途清算及费用相关账户。正式科目、借贷方向、负债/权益属性由财务确认后配置。

不能直接用“全部客户余额 = Slash余额”判断对错：还可能有其他托管位置、平台自有资金、渠道结算义务或已证明的时间差。建立从相关内部控制账户到每个上游资金池的明确核对关系，逐币种列出连接项。

上游可消费额度不能视作现金资产。cash/credit/debit、available/posted分别保存，采用来源文档和产品语义映射，不按名字相同就拼接。Slash文档特别说明借记账户交易的 accountSubtype 使用 cash，而 Balance.type 使用 debit；需由账户产品上下文映射。

官方依据（本轮核验2026-09-07）：[Balance](https://docs.slash.com/api-reference/schema-balance)、[Transaction](https://docs.slash.com/api-reference/schema-transaction)。这不替代本连接产品、资金池及结算模式的确认。

### 3.3 稳定归属与来源隔离

- 内部使用稳定的 customerId、cardId、ledgerAccountId；来源定位至少含主体、provider、connectionId、resourceType、externalId。
- 资金归属与上游卡持卡人/商户名称无关。绑定记录有有效期、版本、操作者和依据。
- 每笔经济事项保存发生时采用的归属/账户映射版本；变更当前卡用户不能悄悄移动历史消费、退款或资金余额。
- 有余额、授权占用或未结事项的卡片改绑，需要业务迁移政策；V1不自动按当前归属重分历史账。
- 历史来源补录、人工入账与上游同步采用同一经济事项引用，防止人工先处理后，补同步又入账一次。

## 四、统一的记账口径

1. 每个账户：`期末账面 = 已确认期初 + 本期入账增加 − 本期入账减少`。期初缺失时不能宣称余额闭合。
2. 每张凭证在同一账本、同一资产内借贷平衡。金额用整数最小单位或精确十进制，API返回字符串；不同资产独立核对。
3. pending授权只改变有证据的占用；posted按实际金额入账。授权100、结算101是同一消费的阶段，不计为201。
4. 原币消费与账户扣款是同一经济事项的两种金额维度，不能各扣一遍。
5. 退款按真实退款金额及时间入账；可另外按原订单归属月分析，不重写消费月份的账本。
6. 费用信息与独立费用流水通过确认关系去重。上游成本、向客户收费及平台收入分别记录；未知费用保持未知。
7. 已入账返现及其冲回才影响相应账；预计返现不能提前抵消费。
8. OTC保存固定报价方向、版本、成交比例、费用和交割金额。默认1 USDT=0.99 USD仅是客户报价；没有真实成本不能把价差直接认定为利润。双币通过兑换清算账户分别平衡，不直接相加资产数量。
9. 金额精确累计后才显示两位。保留USDT完整底层精度；下钻、导出提供精确金额。展示舍入差与真实未解释差异分列。
10. 已入账来源后续更正，通过关联更正/冲正凭证处理，不更新原分录。未知结果先查询核对，不重复付款或释放资金占用。

## 五、三层核对与差异流程

| 层 | 核对对象 | 通过条件 |
|---|---|---|
| 内部账 | 分录、账户期初期末、客户分户、平台控制账户 | 每币种凭证平衡；分户汇总等于相应控制账户；无重复经济影响或孤立分录 |
| 业务账 | 订单、审批、执行、消费/退款/费用与账本 | 实际完成事项具备正确账务影响；待执行、拒绝、授权占用不被计为已入账收支 |
| 外部账 | 每个上游账户/余额类型/币种及链上资产的实际记录 | 已确认来源期初/期末、全期间流水与内部对应记录可核对；每项时间差有证据和到期跟进 |

资金池核对展示：内部应有 → 已证明且有符号的时间/结算差调整 → 可比应有 → 来源实际 → 未解释差异。桥接项只解释差异，不凭空生成资金，不将不明差额塞入“其他”。

先核对笔数、身份与金额，再核对余额；正负差异不能相互抵消后显示“无异常”。同一经济事项导致多个核对项报警，应关联一个主差异，避免重复报告损失。

差异分类：缺内部账、缺来源记录、金额不一致、币种/单位不一致、归属不明、重复资金影响、截止时间不一致、在途超期、期初缺失、同步范围不完整。

- 核对结论：未核对 / 数据不足 / 已匹配 / 有差异。
- 处理进度：待分派 / 处理中 / 待复核 / 已关闭。
- 已解释的时间差保留为待跟踪项；整体不得显示无条件“已对平”，未解释差为0也不能掩盖来源覆盖不足。
- 关闭需要原因、证据、处理动作和复核记录；金额已纠正还需重跑核对通过。财务调整走独立审批和不可变凭证，不提供“修改余额使其一致”。

## 六、后台页面方案

将主入口放到“资金与财务 → 资金对账”；“风险与合规 → 风险监控”保留行为分析，通过差异单互相跳转。旧 `/reconciliation` 地址保留；原来源关联调查放入来源明细或兼容入口。

页面顶部固定展示数据范围（主体、账本、币种、渠道账户）、日切时区、期间、核对批次与版本、来源截至时间、完整性。美元与USDT分开切换；无混合“资金总额”大数字。

四个标签：

1. **日终核对（默认）**：账户/资金池、币种、期初、本期增加、本期减少、应有期末、来源实际、已解释差异、未解释差异、结论、待处理数。金额右对齐，操作最后。
2. **客户分户**：用户名称/邮箱、主钱包、卡分户合计、账面合计、已知占用、可用口径及完整性。点击进入客户对账单，再下钻到具体卡和分录。
3. **上游资金池**：渠道连接、账户、余额类型、币种、内部对应控制账户、来源余额、来源时点、核对结果。不得把cash与credit直接拼成现金余额。
4. **差异处理**：按类型、责任人、账龄、金额、客户、渠道及处理状态过滤；显示首次发现、最近核对、截止时间和下一步。

详情页左侧：余额计算过程和逐笔核对表；右侧：责任人、处理意见、证据、复核与关闭。每条明细可打开交易抽屉或跳转卡片、OTC、出金、管理资金操作单；复杂差异采用独立页。

“查看怎么算”显示真实公式参数与完整金额，而非解释性模板。空数据、未映射、接口失败、未采集、确认为零分别显示。颜色配合文字；不堆装饰图表。

客户对账单默认字段：时间、业务类型、关联订单、收入、支出、账面余额、占用变化、凭证。内部转入转出单列“内部划拨”，不计入客户外部充值/提现总额。

## 七、数据、接口与日切

拟议模型（名称可按正式服务规范调整，均非已实现）：

- LedgerAccount / Journal / Entry：主体、客户/卡归属、资产精度、科目、记账时间、业务时间、经济事项唯一引用、借贷、来源及更正引用。
- Hold：来源授权/出金申请、占用账户、有效金额及释放证据；内部限制独立。
- AccountMappingVersion：内部账户、上游连接/资金池、资金角色、有效区间、确认依据。
- SourceObservation / ImportBatch：脱敏来源、来源时间、采集时间、游标/覆盖边界、错误、内容摘要；人工报表导入亦保留来源与去重记录。
- ReconciliationRun / Item / Difference：固定范围、期初依据、内部账本截点、来源版本、规则版本、金额、结论、关系证据、处理历史。

建议服务能力：账户对账单、客户余额拆解、核对批次创建/查询、批次明细、差异详情/分派/提交处理/复核、受权限控制的导出。复用现有权限主体，区分查询、导出、运行、调查、复核、账务调整；查询端点无写资金副作用。

所有筛选、排序、统计、分页、导出在服务端执行；导出固定批次版本，不能一边翻页一边混入新状态。批次创建及纠正操作幂等；流水不能以orderId、当前名称、同卡同金额作为唯一去重依据。

建议日切默认按运营选定时区配置，界面明确标注；存储UTC并使用左闭右开区间。不能擅自把当前“UTC显示”推定成已经批准的财务日切政策。

执行顺序：人工同步/导入 → 核实完整性 → 固定可比期间与来源时点 → 内部账核对 → 业务逐笔匹配 → 上游核对 → 分派差异 → 复核 → 生成可追溯日终报告。

来源余额若只提供非日切时点：只能做该时点的核对，或在获得完整桥接流水后还原日切；不能把最新余额直接当昨日收盘。仅采集40张卡或30天卡交易不足以核对整个资金池，还需要该池全部会影响余额的非卡流水与完整期间。

迟到清算、退款、更正触发受影响批次的新版本；保留旧报告及重述原因。客户历史对账单按既定记账政策出具，不让新版本静默改写已发送报告。

## 八、贯穿验收例子

以下全为内部模型的合成数据，不代表真实费率、资金池结构或已批准会计政策。

客户最初有USD1000，无其他占用；管理转入卡USD300。消费原币CNY720，授权USD100，最终posted USD101；单独收费USD1.01；部分退款CNY360，实际入账USD49.80。

| 阶段 | 主钱包USD | 卡账面USD | 已知授权占用USD | 客户账面合计USD |
|---|---:|---:|---:|---:|
| 期初 | 1000.00 | 0.00 | 0.00 | 1000.00 |
| 管理转入300 | 700.00 | 300.00 | 0.00 | 1000.00 |
| 授权100 | 700.00 | 300.00 | 100.00 | 1000.00 |
| 清算101、确认解除对应占用 | 700.00 | 199.00 | 0.00 | 899.00 |
| 单独费用1.01 | 700.00 | 197.99 | 0.00 | 897.99 |
| 退款49.80 | 700.00 | 247.79 | 0.00 | 947.79 |

结果：净支出USD52.21、原币净消费CNY360。管理转入不是充值收入；授权不与清算累计；费用注释不能再记一次；CNY不是新增钱包余额；上述例子不能推导Slash资金池期末，外部资金池还需独立期初和完整流水。

另验收：跨月/多次退款、全额原币退款但美元差额不同、返现待入账及冲回、未知费用、缺失授权、不同连接同ID、改绑后退款、部分交割、未知出金结果、重复导入/回调、两个相反差异净额为0、USDT小于0.01差额、缺期初/截断分页/过期快照、旧报告重跑。

## 九、实施顺序与放行条件

1. **确定口径和账户图**：从现有实际账户资料核实内部账本权威、客户余额层级、上游资金池、币种精度、有效期初。不得直接将Demo种子变生产期初。
2. **完成账本纵向闭环**：选一个隔离用户、一张卡、USD，跑通上例及每笔双边账务；账户余额、明细、汇总完全一致后再扩展OTC与其他资产。
3. **服务端核对与页面**：持久化批次/差异、三层核对、四个标签、下钻和导出；明确旧计算页退出正式结果职责。
4. **只读渠道并行核对**：保持原业务账本权威，完整导入来源并影子核对；差异解释和补采集，不接管实际资金操作。
5. **正式账务接管（如后续决定）**：另行审批迁移方案、期初对照、账户映射、去重切点和回滚；明确旧/新系统各业务的唯一写入方，防止两个系统同时扣客户余额。

放行要求：同一输入重跑结果相同；精确金额无未解释差额；可重建客户余额；来源范围不足时始终显示数据不足；任何更正有证据和复核；拒绝/超时/重试不多扣、不重记、不乱释放；客户隔离和权限验证通过。具体性能规模与同步覆盖目标需实测。

待业务/财务确认，不阻碍先写隔离验收模型：正式权威账本及期初来源；客户消费扣账/手续费承担规则；Slash资金池产品与结算关系；USDT网络与执行精度；OTC真实成本与收费规则；日切时区及关账重述政策；卡改绑及历史退款归属；差异处理权限与时限。负责人待分配。
