# 交易、订单与资金领域规范

当前 Go 基础及生产范围见 [文档索引](../README.md)。下方金融设计、F 场景不是已实现或全部已通过的能力；旧 Node/SQLite 本地服务的最新契约与验证见 [当前状态](../current-state.md)；服务、迁移和私有数据未纳入当前仓库。本文目标场景不能视为正式 Go 已实现或本次全部重跑。

更新日期：2026-09-07。状态：DESIGN；以下名称为内部模型，不是 Slash 原生字段或已完成数据库表。

渠道事实见 [Slash 接入规范](../integrations/slash.md)，接口见 [契约](../api/contract.md)。

## 1. 资金事实的权威来源

| 数据 | 权威依据 | 不得替代为 |
| --- | --- | --- |
| 渠道余额 | 已核验账户、类型、币种及时点的渠道快照 | 交易列表简单求和、卡片限额 |
| 内部客户资金归属 | 原业务账本及生效映射 | Slash accountId、登录账号或商户订单号 |
| 实际入账资金流 | 有证据的入账交易/账本记录 | 授权申请、pending 金额、退款意图 |
| 经营分析 | 明确口径的派生投影 | 真实可出款余额 |
| 对账结果 | 可比范围的事实及差异证据 | 为配平而编造的调整 |

当前本地卡预算、Demo 钱包与 Slash 来源账户分开；不得把已在来源账户体现的历史消费再扣一次内部预算。

## 2. 模型与标识

| 模型 | 必要职责与字段组 |
| --- | --- |
| ChannelConnection | provider、连接 ID、环境、合法实体范围、能力、凭据引用；不存前端可读秘密 |
| AccountMapping | 内部 customer/account 与来源账户/子账户的关联、资金角色、有效期、确认依据 |
| BusinessOrder | 内部业务 ID、业务类型、归属、订单维度状态；商户 orderId 仅作外部参考 |
| ProviderTransaction | 唯一来源定位、来源两层状态、当前金额/日期、脱敏来源版本、映射版本 |
| AuthorizationObservation | 有来源证据的授权金额/变化与观察时间；缺少历史就标未知 |
| FundMovement | 每项实际入账影响、所属账户、金额、业务类型、来源证据、纠错链 |
| TransactionRelation | from/to、refund/fee/reversal 等类型、证据、确认状态、有效期、确认人 |
| BalanceSnapshot | 来源账户、币种、余额类型、available/posted、computedAt、collectedAt |
| SourceEvent / Delivery | 通知身份与每次投递、验签结果、接收和处理状态、重试 |
| ReconciliationRun / Difference | 时间范围、覆盖、规则版本、证据集合、差异原因、处理记录 |

唯一键至少包含稳定数据隔离范围、channelConnectionId、resourceType、externalId。当前客户主体为 customer，不等同身份服务 tenant；新增 platform tenant 前必须单独决定模型。共享渠道账户应在连接下只保留一份来源记录，通过授权及分配关系服务多个客户，不能每个客户复制资金后求和。

业务订单可关联多笔交易；退款/费用/冲正关系独立建模。启发式匹配只能成为候选，不得进入已确认订单净额。支持部分分配时，每条关系带精确分配金额，分配合计不得超出可分配来源金额；外币退款需按对应金额维度校验，不能只比较美元退款是否超过原美元消费。

## 3. 多维状态

建议内部维度如下，具体枚举需在机器契约中定稿：

- authorization：unknown、pending_approval、held、partially_released、released、declined、expired、not_applicable。
- posting：unknown、pending、posted、failed、not_applicable。
- refund：unknown、none、pending、partial、full、failed、not_applicable。
- dispute：unknown、none、open、won、lost、closed、not_applicable。
- reconciliation：not_checked、insufficient_data、matched、unmatched、mismatch。
- sync：never_synced、syncing、fresh、stale、error、partial。

必须保存维度来源证据。`none` 要求相关范围已查全，不能由字段缺失推出；`full` 需要可信关系、可比金额与明确业务规则，不能按美元比例推算原币全退。

源交易状态和订单聚合状态分层：一笔退款失败不改变原消费已入账；争议开启不自动改变入账金额。未知或矛盾来源组合触发映射异常，但保留原始事实。

## 4. 金额、时间和汇率

新模型金额采用 `signedAmountMinor` 十进制整数字符串、`currency`、`scale`，正为流入/正余额、负为流出/负余额，零为零。币种元数据与来源单位映射必须版本化。当前 Go `amountMinor + direction` 契约不自动替换，新旧由显式适配处理。

- 数据库用有界整数或精确定点数并检测溢出，JS 使用 BigInt/十进制库；数字解析发生精度丢失后不能靠转字符串修复。
- `accountAmount`、`originalAmount`、`authorizedAmount`、`postedAmount`、退款金额和费用金额分别表达，不混用。
- `providerFx` 与 `reportingFx` 分离，包含方向、十进制 rate、来源、可知的时间、用途和证据。来源未给时间时允许未知，不凭空创建授权/入账汇率。
- 采用本系统报表折算时注明舍入策略、逐笔或汇总折算、汇率来源和规则版本，不能冒充渠道实际扣款。
- UTC 保存事件/入账/采集时间；业务查询使用指定时区，区间统一 `[from,to)`。授权日、入账日、退款日和订单归属日分开。
- 卡注销、客户升级、归属调整不得重写历史所有权；归属映射应按有效期解释。

## 5. 资金统计不变量

1. 待入账与已入账分开；同一消费由 pending 变 posted 只贡献一次入账支出。
2. 每个实际资金影响有稳定 effectKey，不能按 eventId 或 mappingVersion 新建一笔支出。
3. 来源观察记录追加保留；派生投影可版本化重建。同一来源后补修正以明确替代/纠正链处理，不能把旧值与新值都累计。
4. 费用注释、费用明细拆分与独立费用流水只有一个记账来源；返现信息不自动视为已收到返现。
5. 退款以实际入账计资金流；未匹配退款可计入账户资金流，但不能编造原订单归属。
6. 不同原币分别汇总。内部转账仅在明确合并范围且两端匹配时消除，单账户报表保留两端各自影响。
7. 订单消费净支出 = 已入账消费支出 + 已确认分配的费用 − 已确认入账退款/费用返还；其他返现或调整是否包含须单列口径。账户净资金流则包含范围内所有已确认实际入账。
8. 授权金额差不等于汇兑损益；余额类型差不等于冻结；额度不等于资金。
9. 重放、重新导入、映射升级、补同步前后，未发生来源纠正时总资金影响必须不变。

### 外币演示算例（内部假设，非 Slash 行为证明）

| 观察/事件 | 原币 | USD 已入账影响 |
| --- | --- | ---: |
| 授权观察 | CNY 720 | 0，USD 100 只是已知授权观察 |
| 消费入账 | CNY 720 | -101.00 |
| 独立费用入账 | 不与原币消费相加 | -1.01 |
| 已确认关联的部分退款 | CNY 360 | +49.80 |

账户净变化为 -52.21 USD；该订单净支出 52.21 USD，原币消费净额 360 CNY。不据此生成虚构汇率、不按授权 USD 100 重算退款、不把费用再扣一次。若只拿到最终交易，授权金额应未知。

## 6. 对账规则

对账分为来源完整性、交易关联、余额核对；分别报告，不能合成一个“成功”掩盖缺口。

只有账户、币种、余额类型、起止时点、归属和全量覆盖都可比，并确认该余额类型适用入账流量恒等式时，才可使用：

```text
预期期末已入账余额 = 期初已入账余额 + 范围内已入账有符号资金流
差异 = 来源期末已入账余额 - 预期期末已入账余额
```

信用可消费余额可能受抵押/额度等其他机制影响，未经证实不能套此式。禁止无条件跨 USD/USDT 或 cash/credit/debit 相加。`available = posted - holds` 仅能作为已验证产品模型或明确 Demo 假设。

输入不全返回 insufficient_data；不叫“少钱”。差异分类至少包含缺失记录、重复、未匹配关系、时间差、FX/费用、归属错误、来源修正、未知原因。容差按币种和政策显式配置；精确整数明细默认应精确相等，不继承通用 USD 1 容差掩盖错误。

批次记录起止快照、覆盖/失败源、规则版本、投影版本、生成时间；迟到退款/费用触发新修订版。人工匹配或处置留审核人、时间和证据，只改变调查状态，不改真实余额。

### V1 内部账本与对账补充（2026-09-07，DESIGN）

实施顺序、页面及核查差异以 [V1 账本与对账规划](reconciliation-v1-plan.md) 为准。

- **归属**：内部 customerId/cardId/ledgerAccountId 为业务身份；来源 ID 只作隔离后的关联。内部卡分户不要求上游具有逐卡资金余额。当前所属用户绑定不等于资金账户已开通或历史资金已划归该用户。
- **余额**：同客户同资产的主钱包、卡分户与其他独立子账户互不重叠，汇总行不能再加一次。逐账户保留期初与凭证；管理转入/转出在合并客户范围内净变动为零，不冒充充值/提现。
- **科目**：客户资金义务、平台资金、上游实际资产、结算应收应付及在途分别映射；不能直接断言客户余额总和等于 Slash 可用金额。正式科目及期初凭证待财务确认。
- **不变量**：同账本同资产每张凭证借贷精确平衡；账面余额可由期初和已入账分录重建。预占、风控限制、审批与实际执行分开。更正追加关联凭证，不改已入账分录。
- **跨系统去重**：人工处理、业务执行与来源补同步关联同一经济事项，重复交付不能重复入账。冻结或改绑不能重写原交易归属；后续退款根据原事项映射及已批准迁移政策归属。
- **金额显示**：USD/USDT 默认两位只是显示要求；保留原始精度，先精确汇总再显示。小于0.01的真实差额可展开、导出，不能按0.00自动忽略。OTC默认1 USDT=0.99 USD为可配置客户报价，不是利润或上游成本证明。

核对结论、作业执行状态、差异处理进度分别保存。结论归为未核对、数据不足、已匹配、有差异；逐笔未匹配与金额不符继续作为明细原因保存，与上文状态维度兼容，不能只改显示枚举丢失原因。具体机器枚举在正式契约中版本化。

内部账、业务账、外部账分别报告笔数/身份/金额/余额核对。外部可比应有 = 内部对应控制账户应有 + 有证据的有符号桥接项；未解释差异 = 来源实际 − 可比应有。桥接项必须有原记录、方向、期限和负责人，不能是配平插值；已解释在途仍需跟踪。

覆盖不全、期初未知、时点不一致、分页截断、来源失败均不能显示全量对平。相反差异不能相互抵消，多个检查命中同一事项也不能重复报告损失。复核关闭保留原核对结论；金额纠正需独立审批、凭证和新批次核对证据。

服务端固定范围、日切时区、账本截点、来源观察及规则/映射版本，明细、汇总与导出使用同一版本。迟到数据生成新修订，不静默覆盖已出具报告。财务日切需配置确认，不能由页面UTC显示或API报表默认时区推定。

当前独立 Demo 账本仅可复用机制；正式切换另需期初验证、账户映射、经济事项去重切点、唯一写入方及回滚方案，禁止新旧系统同时扣同一客户余额。

## 7. 前端职责

交易列表显示来源、原币/记账金额、状态维度和数据时点；详情显示观察时间线、真实事件证据、关联、费用及差异。缺失历史不补造完整流程图。

资金页按账户/币种/类型分组；渠道失败显示不可用或上次快照时间，不能显示为零。零、未知、不适用、不支持和获取失败采用明确不同文案；汇总由后端计算，分页列表不参与全量总计。
