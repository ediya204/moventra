## 2. 当前代码边界（LOCAL）

子项目的启动、路由及接口依据见 [API](../services/api/README.md)、[客户端](../apps/client/README.md)、[后台](../apps/admin/README.md)、[共享模块](../packages/shared/README.md)和[隔离服务](../services/local-workspace/README.md)。能力和发布进度不在本页重复维护。

Go 基础 `transactions` 采用 USD/USDT、正数 amount_minor 加方向、pending/succeeded/failed；来源唯一约束为 `(source, external_id)`。多渠道、多状态及其他币种需显式迁移/适配，不静默替换既有契约。

独立 channel_records 按连接、导入版本、资源和外部 ID 保存白名单。后台渠道权限、客户逐卡分配、客户身份读取权限各自校验；渠道金额不写入基础 transactions 或余额。online_test、Blnk shadow 和来源观察有独立数据与职责，不能混账。

已恢复的本地 Demo 可复用机制及测试，不把模拟版本号、预算、冻结或同步行为当作真实渠道保证。源码存在不证明对应生产功能可用。

## 3. 目标及不在范围内的事项（DESIGN）

目标：低耦合、多渠道、可审计的只读交易与资金视图。首个真实接入候选为 Slash，保留其他支付、发卡和账户渠道适配能力。

依赖方向：

```text
Slash / 其他渠道 → 渠道适配层 → 来源记录与版本 → 统一查询投影 → 查询 API → 前端
                                   ↓                ↓
                              同步覆盖/审计       对账/预聚合
旧系统客户关系及账本 → 明确授权的只读来源与映射 ──────────┘
```

旧系统继续保有原有账务职责；新系统不自动改变资金所有权、客户账本或授权决策。需要读取旧数据时，另行选择经授权的 API、只读副本或报表源；不能默认直连旧主库无影响。

不在首期范围：真实资金操作、自动差异核销、清算执行、授权 Webhook 决策、客户敏感卡信息扩展。未来若升级成资金执行系统，必须另立双重记账、资金预占、审批、幂等和冲正方案并获得授权。

### 2026-09-07：内部账本与对账方向（DESIGN）

客户归属、内部卡身份、卡资金分户、审批及业务账本由我们系统负责；Slash 作为上游事实与执行通道。内部卡分户不以 Slash 提供逐卡余额为前提。现有权威账本在正式接管前继续负责实际记账，本地隔离 Demo 不自动升级为生产账本。

后续按“内部账 → 业务逐笔 → 上游资金池”三层核对，按币种保存期初、变动、期末和证据。主钱包与卡分户不能重复计资产，授权占用不计收支；来源不全必须显示数据不足。页面目标为日终核对、客户分户、上游资金池、差异处理四个标签。完整方案见 [V1 账本与对账规划](domain/reconciliation-v1-plan.md)。

本次仅同步本地文档，不变更账本权威、不执行迁移或资金动作。正式科目、期初、结算关系、日切与复核政策仍需业务/财务确认；隔离实现、真实渠道验证、部署和业务验收分别记录。

## 4. 开发协作顺序

1. 后端盘点字段、数据规模、来源权限、适配器能力与数据库差异；前端盘点页面和显示语义。
2. 联合确认领域规则、契约、兼容方案、未知项处理；重要选择记录决策日期、理由与替代方案。
3. 先用隔离 Demo 完成映射、接口和测试；保留旧路由及旧 DTO。
4. 经授权后接入测试渠道，验证金额、时间、费用、状态和同步的真实语义。
5. 完成回填计划、对账覆盖、告警、权限、负载测试与回滚演练后，另行申请上线。

每个待核实项必须有负责人/确认人、阻塞阶段和证据；负责人未分配时明确写“待分配”，不默认开发人员能决定金融政策。

## 5. 分阶段交付与通过条件

| 阶段 | 产物 | 通过条件 |
| --- | --- | --- |

| P3 真实测试接入 | 授权测试凭据、产品范围、脱敏实证 | 核心金额/余额和状态与来源可核对；未知能力不冒充支持 |
| P4 生产准备 | 迁移、回填、压测、告警、运行手册和回滚 | 明确授权后执行；未解决高风险项阻止相应功能上线 |

## 6. 大数据量设计门槛

以下参数当前均待采集：总历史记录、日新增、峰值通知、回填年限、保留期限、查询并发、常用时间跨度、P95 延迟目标、同步新鲜度目标、源接口配额、导出大小。未测量前不承诺容量或采购规格。

- 以已有 PostgreSQL 为候选评估查询与存储；SQLite 仅作为历史本地 Demo，不默认承担生产大规模负载。
- 明细使用服务端筛选、稳定游标和适用索引，汇总使用独立聚合，不在前端下载全量数据。
- 索引先覆盖主体/连接/账户/时间/稳定 ID 等实际查询；分区策略需兼顾旧交易更新，不只按新增日期设计。
- 实时同步与历史回填分队列和配额，限制并发并支持背压、重试和断点续传。
- 聚合须支持迟到退款、费用与历史修正；缓存键包含授权范围、口径版本、币种、时区和数据版本。
- 大导出异步化、限额、授权复检和过期下载；禁止无限时间查询和同步全量响应。
- 只有实测表明需要，才引入额外分析库或冷热存储。Slash Analytics 的能力不能推定为无限导出能力。
- 验收报告必须记录数据规模、查询组合、P95、内存、锁等待、队列积压、回填速度及重复数据率。

- 保留本次命令及结果；跳过的测试明确标注，不以历史结果代替。
- 数据迁移使用增量文件，不修改已应用迁移；生产备份、恢复验证和回滚需独立批准。
