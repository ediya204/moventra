# 业务闭环开发与验收标准

日期：2026-09-13。适用：后续页面、交互和前后端开发。本文是开发规则，不代表已有功能通过验收；本次仅整理规范及首批静态差异。原有金融、授权及发布边界继续有效。

## 1. 交付单位

每次交付以一条可验证的业务流程为单位。页面、按钮、接口和表属于该流程的组成部分，单独存在不能证明流程完成。开发者负责调查依赖与异常路径；用户负责业务政策和范围选择，不要求用户逐个指出断链按钮。

只读流程：入口 → 筛选列表 → 独立详情 → 关联对象 → 返回原上下文。

涉及处理的流程：客户发起 → 服务端保存 → 后台查询及处理 → 客户查询同一事项的结果 → 审计与异常恢复。审批、执行、渠道确认及记账按领域规则分别表达。此类流程须先在已授权的隔离环境实施，本文不开放真实资金写入。

## 2. 开发前必须填写的流程卡

为每条流程分配稳定编号 `FLOW-xxx`，使用下表；没有信息的字段写“待核实”及阻塞步骤，不能默认为已支持。

| 项目 | 必填内容 |
| --- | --- |
| 目标及范围 | 谁要完成什么任务；验收环境；本批明确包含的起点和终点 |
| 基线 | 仓库、分支/提交、相关未提交文件；无法取得提交时记录文件哈希；应用及服务启动方式 |
| 页面关系 | 客户端/后台分别列列表、二级、三级和关联入口；写出真实路径、路由参数和返回目标 |
| 业务身份 | 业务记录 ID、客户主体、来源连接与资源 ID；两端如何查到同一事项 |
| 数据依据 | 哪个服务持久化、哪个来源权威、是否模拟、数据时间/版本、覆盖范围 |
| 接口链 | 页面调用 → 客户端 transport → 同域网关 → 后端 handler → 查询/存储；逐层注明现有或待实现 |
| 状态及操作 | 当前状态、允许的动作、角色、前置条件、下一状态、不可执行原因及失败恢复 |
| 跨端变化 | 哪个动作使哪些列表、详情、计数和待办变化；采用重新查询/轮询等何种方式及更新时机 |
| 权限 | 客户所有权、运营资源授权、MFA、字段裁剪、直接请求和换 ID 的预期拒绝结果 |
| 验收 | 测试编号、数据准备、角色、步骤、结果断言、执行日期及证据；不适用项注明理由 |
| 待定决策 | 决策内容、负责人/确认人、阻塞阶段及兼容方案；无人承接时写“待分配” |

## 3. 多级页面标准

1. 每个需要分享或刷新恢复的业务详情都有稳定 URL；关联对象采用经授权的稳定 ID，不靠列表中已加载的数据猜测。短详情可用抽屉，但必须能从 URL 恢复对象。
2. 一级至三级及浏览器前进/后退保留合理的筛选、排序、页码和当前标签；敏感数据与凭据不得进入 URL。无来源上下文的直接访问也有有效返回入口。
3. 记录必须属于路径中的客户、卡片或订单。伪造父子关系、跨主体或跨连接 ID 由服务端拒绝，不能仅靠隐藏链接。
4. 刷新、复制链接、新会话重新认证后仍能查询持久化对象。隔离演示若重置数据，明确说明限制，不能标为持久化闭环。
5. 每页覆盖加载、无记录、筛选无结果、无权限、对象不存在、服务失败、数据过期；失败不能显示为零，错误页提供适当重试或返回入口。
6. 每个可点击动作必须有实际目标及结果；尚未接入的能力说明原因，不用通用成功提示模拟完成。只有缺失后端能力时，不为了消除空页而放开 DEV 路由。

## 4. 前后台和服务端标准

- 同一经济或业务事项使用可追溯的关联关系。客户端和后台可展示不同字段，但不能各自维护一份独立的权威状态。两端无共同数据源时标记“未联通”。
- 前端显示成功应有服务端确认依据。超时或结果未知时提供状态查询；有副作用的重试复用幂等标识，不把再次点击当作新事项。
- 处理结果应在列表、详情、待办中一致；并发处理过期版本时拒绝或返回最新状态，不静默覆盖。审批链与审计必须能够关联原申请。
- 筛选、分页、总数和汇总注明范围。默认前 50 条、某批导入或局部快照不得冒充全量；跨页详情不应依赖首页缓存。
- 接口 schema、transport 白名单、网关、handler 及权限必须一起验证。HTTP 200、编译成功或接口单测通过都不能单独证明页面已接通。
- 客户端与运营后台只在有授权关联时联通；不能为实现同屏数据而把未归属的渠道记录开放给客户。

## 5. 完成定义与证据

每条流程同时填写两组状态，避免“代码存在”被理解成“已上线”。

能力等级：`仅展示`、`局部交互`、`隔离闭环`、`正式服务接通`。未实测标“待验证”，不强行评级；局部闭环需写明覆盖步骤。正式服务接通要求指定版本的真实服务实现及前后端联调证据，不代表生产发布。

证据维度：设计、本地实现、自动化测试、浏览器流程验收、真实渠道验证、部署。每项写“通过/失败/未执行/不适用”、环境、版本、日期和证据。不适用必须说明原因；历史测试只作历史证据。

通用验收用例按流程挑选并写明断言：

| 编号 | 检查 | 通过条件 |
| --- | --- | --- |
| E01 | 主流程 | 从用户入口达到声明终点；对象 ID 和数据来源一致 |
| E02 | 二三级导航 | 下钻、关联跳转、返回及前进后退正确还原上下文 |
| E03 | 刷新与深链 | 详情刷新、复制链接、认证恢复后不依赖前页内存 |
| E04 | 跨端一致性 | 两个独立会话查询同一事项；后台处理后客户按约定刷新看到同一结果 |
| E05 | 直接越权 | 换主体/资源/连接/父子 ID、缺少 MFA 或权限时服务端拒绝且无数据泄漏 |
| E06 | 错误恢复 | 断网、401、403/404、5xx、未知结果不会伪成功或误显示零；恢复路径可用 |
| E07 | 重复与并发 | 重复提交、双人同时处理、重放不会重复改变状态或资金影响 |
| E08 | 查询完整性 | 超过一页的数据可正确查询；筛选/分页/详情/汇总口径一致且公开覆盖限制 |
| E09 | 审计与金额 | 适用时记录可追溯、金额精确，引用并通过对应 F/R 资金场景 |

只读链 E04 可改为两端对授权同一投影的查询一致性；没有跨端业务归属时注明不适用，不能强行绑定。E07 写操作不适用时仍需考虑读取竞争及旧响应覆盖。自动化至少覆盖关键契约、权限和状态风险；浏览器验收验证实际路由、交互及两端状态。截图不能代替状态断言。

## 6. 执行顺序

1. 按[首批整改清单](connectivity-baseline-2026-09-13.md)核实工作区和正式源码版本，保留现有未提交工作。
2. 每次选择一条流程，补全流程卡、差异及兼容方案。已获授权的常规实现继续推进；涉及未定业务政策或范围扩大时只明确询问该决策。
3. 从服务端契约及身份归属打通到列表、详情、关联对象、跨端状态，再补错误恢复；复用现有组件和已验证业务机制。
4. 按本批范围运行测试与浏览器验收；记录未通过或未执行项，不能用页面数量计算业务完成度。
5. 本地闭环通过后再进入获授权的真实渠道验证及发布阶段。后续批次保持已验收链路回归。

旧文档保留为历史记录；新状态引用本次证据更新，不静默追认历史功能。本标准不改变既有金额、状态枚举、金融契约或生产权限。
